**PART A — Compute test fixtures manually:**

You must compute expected fingerprint values by following the SISP algorithm step-by-step. This is critical — do NOT use the PHP functions to generate "expected" values (that would be circular). Instead, compute by hand.

**Request Fingerprint Fixture (`tests/fixtures/fingerprint-request.php`):**

Return an array with known inputs and the expected output.

Use these fixed inputs:
- pos_auth_code: `"TESTAUTHCODE123"`
- timestamp: `"2026-04-16 14:30:22"`
- amount: `"1500"` (will become 1500 * 1000 = 1500000 in hash)
- merchant_ref: `"WC42-20260416143022"`
- merchant_session: `"Sabcdefghijklm"`
- pos_id: `"900001"`
- currency: `"132"` (CVE)
- transaction_code: `"1"`
- entity_code: `""` (empty — optional field excluded)
- reference_number: `""` (empty)
- token: `""` (empty)

Compute the expected fingerprint manually:
1. Compute sha512_base64 of "TESTAUTHCODE123" = base64_encode(hash('sha512', "TESTAUTHCODE123", true))
2. Build the base string: {step1_result} + "2026-04-16 14:30:22" + "1500000" + "WC42-20260416143022" + "Sabcdefghijklm" + "900001" + "132" + "1"
   (Note: entity_code, reference_number, token are all empty, so they are NOT appended)
3. Compute sha512_base64 of the full base string = base64_encode(hash('sha512', $baseString, true))
4. That final hash IS the expected_fingerprint

Also include a second fixture WITH optional fields:
- Same as above but entity_code: `"54321"`, reference_number: `"67890"`, token: `"tokenXYZ"`
- When entity_code is "54321": absint(ltrim("54321", "0") ?: "0") = 54321
- When reference_number is "67890": absint(ltrim("67890", "0") ?: "0") = 67890
- token: trim("tokenXYZ") = "tokenXYZ"
- Append "54321" + "67890" + "tokenXYZ" to base string before final hash

Also include a third fixture testing the leading-zero stripping in entity_code:
- entity_code: `"00042"` → absint(ltrim("00042", "0") ?: "0") → ltrim gives "42", absint = 42 → appends "42"

**Response Fingerprint Fixture (`tests/fixtures/fingerprint-response.php`):**

Use these fixed inputs:
- pos_auth_code: `"TESTAUTHCODE123"`
- message_type: `"8"`
- clearing_period: `"30"`
- transaction_id: `"TXN999888"`
- merchant_ref: `"WC42-20260416143022"`
- merchant_session: `"Sabcdefghijklm"`
- purchase_amount: `"1500"` (will become 1500 * 1000 = 1500000)
- message_id: `"MSG001"`

- timestamp: `"2026-04-16 14:31:00"`

- entity_code: `"ENT01"`
- client_receipt: `"YES"`
- additional_error_message: `""`
- reload_code: `"0"`

Compute expected response fingerprint:
1. sha512_base64("TESTAUTHCODE123") — same as request
2. Base = {hash} + "8" + "30" + "TXN999888" + "WC42-20260416143022" + "Sabcdefghijklm" + "1500000" + "MSG001" + "************1234" + "APPROVED" + "2026-04-16 14:31:00" + "REF789" + "ENT01" + "YES" + "" + "0"
3. sha512_base64 of that base string

IMPORTANT: Use PHP's actual hash() and base64_encode() to compute these values during fixture creation. The key insight is: the fixture file itself can compute the expected value at load time using raw PHP primitives, as long as the fixture does NOT call the Vinti4 classes. This avoids circularity — the fixture uses hash() + base64_encode() directly, while the code under test uses Vinti4_Fingerprint which wraps the same primitives. If the class has a bug in field ordering, the test will catch it.

The fixture file should return:
```php
<?php
return [
    'request_basic' => [
        'inputs' => [... all the input fields ...],
        'expected_base_string' => $computedBaseString, // for debugging
        'expected_fingerprint' => base64_encode(hash('sha512', $computedBaseString, true)),
    ],
    'request_with_optional' => [...],
    'request_leading_zero_entity' => [...],
    'response_success' => [...],
];
```

- `test_parse_order_id_invalid()`: `vinti4_parse_order_id_from_ref('INVALID')` → `0`
- `test_parse_order_id_empty()`: `vinti4_parse_order_id_from_ref('')` → `0`

- `test_is_success_message_type_false()`: Assert false for '0', '1', 'N', '', '8.0' (type coercion check)

**tests/Test_Logger_Mask.php:**
- `test_mask_long_code()`: `Vinti4_Logger::mask_auth_code('ABCDEFGHYZ')` → `'ABC***YZ'` (10 chars: first 3 + 5 asterisks + last 2)
- `test_mask_short_code()`: `Vinti4_Logger::mask_auth_code('Abcd')` → `'A***'` (4 chars < 6: first char + asterisks for rest)
- `test_mask_empty()`: `Vinti4_Logger::mask_auth_code('')` → `''`
- `test_mask_six_chars()`: `Vinti4_Logger::mask_auth_code('ABCDEF')` → `'ABC*EF'` (6 chars: first 3 + 1 asterisk + last 2)
- `test_mask_special_chars()`: `Vinti4_Logger::mask_auth_code('AB%CD=12')` → `'AB**12'` (8 chars with special chars: first 3 + 3 asterisks + last 2 — note first 3 is "AB%", which preserves the %)
  Wait: 8 chars, first 3 = "AB%", length-5 = 3 asterisks, last 2 = "12" → "AB%***12"

IMPORTANT: The Logger class has a `class_exists('Vinti4_Logger')` guard. Since bootstrap defines the stub BEFORE requiring the file, the class won't exist yet, so the real class will load. But the Logger also calls `defined('ABSPATH') || exit;` — bootstrap must define ABSPATH before requiring.

Note: Vinti4_Logger::mask_auth_code is a pure static function that doesn't access any WordPress or WooCommerce APIs. It can be tested in isolation.
