# Milestone v1.1: Partial Deposits and Multi-Attempt Payments

**Status:** ✅ SHIPPED 2026-04-18
**Phases:** 9-11
**Total Plans:** 6

## Overview

Extends the shipped v1.0 hosted-card flow with partial deposits and multi-attempt payment requests for existing orders. The key change is moving from single-attempt order-level references to attempt-scoped references and reconciliation. Admin can create partial payment requests, customers pay via SISP 3DS redirect, and callbacks resolve at attempt granularity while preserving existing card redirect behavior.

## Phases

### Phase 9: Attempt Foundation and Persistence

**Goal**: Multiple payment attempts can exist for one WooCommerce order, each with unique reference/session/fingerprint context.
**Depends on**: Existing v1.0 callback and request builder foundations
**Requirements**: ATT-01, ATT-02, ATT-03, ATT-04
**Plans**: 2 plans

Plans:

- [x] 09-01-PLAN.md — Introduce attempt storage model and append-only history helpers on orders
- [x] 09-02-PLAN.md — Add attempt factory service to generate unique merchantRef/session/fingerprint from partial attempt input

**Details:**

Phase 9 introduced the foundational attempt data model. `Vinti4_Attempt_Store` provides append-only history persistence on WooCommerce orders with deterministic chronological retrieval and legacy `_vinti4_*` meta projection for backward compatibility. `Vinti4_Attempt_Factory` is the canonical attempt creation service with unique merchant reference generation (timestamp + entropy), amount-bound fingerprint context, and integration into the checkout flow. The gateway exposes `create_payment_attempt()` as a public entry point for both checkout and future admin flows.

Key decisions:
- `_vinti4_attempt_history` is the canonical append-only persistence key; legacy single-attempt keys are projection-only compatibility outputs
- Chronological enumeration is deterministic using `created_at_gmt` plus monotonic `sequence` tie-breaking
- Factory + Store split: factory creates immutable attempts, store owns persistence/projection concerns

### Phase 10: Admin Partial Request Flow

**Goal**: Admin can send payment requests for partial amounts safely and predictably.
**Depends on**: Phase 9
**Requirements**: PART-01, PART-02, PART-03, REQ-01
**Plans**: 2 plans

Plans:

- [x] 10-01-PLAN.md — Create admin meta box with partial amount form, validation, AJAX attempt creation, and payment link generation
- [x] 10-02-PLAN.md — Add attempt history table, payment progress display, resend link functionality, and diagnostic test

**Details:**

Phase 10 built the admin-facing partial payment request flow. `Vinti4_Admin_Partial_Payment` provides a meta box on WooCommerce order edit pages showing outstanding balance, paid total, and a form supporting fixed or percentage amount modes. Validation blocks invalid amounts (non-numeric, zero, exceeds outstanding, fully-paid). AJAX-driven attempt creation chains through gateway → factory → store → legacy meta projection → payment link generation with copy-to-clipboard UX. Attempt history table shows all attempts with status badges (green/red/amber), and resend links allow re-projecting pending attempts.

Key decisions:
- HPOS dual registration (shop_order + woocommerce_page_wc-orders) for meta box compatibility
- Outstanding tolerance uses +0.01 buffer for floating-point edge cases
- Progress bar uses inline CSS for zero-dependency rendering
- Resend link re-projects attempt to legacy meta and returns payment link for clipboard

### Phase 11: Callback Reconciliation and Compatibility Verification

**Goal**: Callbacks resolve and mutate state at attempt granularity while preserving existing card redirect behavior.
**Depends on**: Phase 9, Phase 10
**Requirements**: PART-04, REQ-02, REQ-03, REQ-04, CARD-01, CARD-02, OBS-01, OBS-02
**Plans**: 2 plans

Plans:

- [x] 11-01-PLAN.md — Refactor callback resolution and idempotency to attempt-level reconciliation
- [x] 11-02-PLAN.md — Add compatibility verification, sandbox card flow checks, and multi-attempt diagnostics logging

**Details:**

Phase 11 refactored the callback handler for attempt-level reconciliation. Callbacks resolve the exact attempt by `merchantRef` before any order mutation. Per-attempt idempotency uses `_vinti4_attempt_{attempt_id}_processed` meta keys instead of order-level processed flag. Partial payments keep order in processing status; `payment_complete()` only fires when outstanding ≤ 0.01. Legacy fallback path preserved for pre-v1.1 orders without attempt history, with `_vinti4_is_legacy_order` diagnostic marking. Structured logging adds `log_callback_outcome()`, `log_validation_failure()` with failure_type classification, and `log_duplicate_callback()`.

Key decisions:
- Attempt-first resolution: find attempt in history, validate against attempt context, fall back to legacy if no history
- Per-attempt processed flag tracks state independently per attempt
- Partial payments set order to 'processing' with detailed note; completes only when fully paid
- Failure type classification: invalid_reference, invalid_session, invalid_fingerprint, amount_mismatch, duplicate_callback

## Milestone Summary

**Key Decisions:**

- Decision: Use `_vinti4_attempt_history` as canonical append-only persistence (Rationale: Immutable audit trail, no destructive overwrites)
- Decision: Factory + Store split (Rationale: Creation concerns separate from persistence/projection)
- Decision: Attempt-first callback resolution with legacy fallback (Rationale: Multi-attempt support without breaking pre-v1.1 orders)
- Decision: Per-attempt idempotency via unique meta keys (Rationale: Each attempt independently deduplicated)
- Decision: Outstanding threshold ≤ 0.01 for completion (Rationale: Floating-point tolerance)
- Decision: HPOS dual registration for meta box (Rationale: Both classic and HPOS order storage backends)
- Decision: Inline CSS for progress bar (Rationale: Zero dependencies)
- Decision: Structured failure type logging (Rationale: Distinguishable diagnostic categories)

**Issues Resolved:**

- Fixed missing `Vinti4_Logger` dependency in bootstrap (was commented-out Phase 7 placeholder)
- Restored feature compatibility registration and admin test panel wiring after accidental removal during Phase 9
- Fixed test amount unit mismatches (SISP '100000' format vs WooCommerce '100' format) in Phase 11 tests

**Issues Deferred:**

- Admin meta box renders for all shop_order posts regardless of payment method (should check Vinti4 gateway) — minor cosmetic
- Redundant `get_paid_total()` calls in callback handler — minor performance
- Amount type variance: stored as string, validated as int, summed as float — consistent in practice but type-fragile

**Technical Debt Incurred:**

- PHP CLI unavailable in execution environment — lint and PHPUnit verification must be rerun before release
- `mark_attempt_completed()` relies on implicit save() via `get_paid_total()` — fragile if refactored
- Logger never initialized in tests (debug=false) — logging paths untested but safe
- E2E SISP flow requires running WP/WC/SISP stack for runtime verification
